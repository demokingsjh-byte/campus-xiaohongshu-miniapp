# ESP32 固件修改需求（2026-09-21）

> 本文前半部分保留 2026-09-21 的现场问题基线，末尾记录本次改造目标。当前默认方案已改为 `omni-realtime`：设备 PCM16LE/16kHz 与 JPEG 送入同一实时多模态模型，模型直接返回文字和 PCM16LE/24kHz 音频；用户转写只用于异步日志。旧 ASR → 图文模型 → TTS 仅在 `chat` / `responses` 回退模式使用，不能再把全部耗时归因于设备。

## 背景：线上实测数据

| 现象 | 实测数据 | 服务端状态 |
|---|---|---|
| 多轮采集拖延 | 16~24s（16216 / 20148 / 24246 ms），偶发正常（1663 / 5533 ms） | 服务端已加静音自动提交兜底（1500ms），但治标 |
| 图片从未上传 | 所有轮次 imageCount=0，无 INVALID_IMAGE 错误码 | 服务端就绪，上限已放宽到每轮 5 张 |
| 空转写失败 | 两轮「语音转写失败」（大概率空音频/纯噪音采集） | — |

## 需求 1（P0）：修复 VAD「说完」判定

**现状**：说完一句话后设备经常判不出结束，靠超时（约 16~24s）才发 `turn_commit`，多轮对话每轮白等十几秒。

**要求**：
1. 采集期间对 PCM16LE / 16kHz / 单声道音频做本地能量检测（建议：滑窗均方根或 max-abs）。
2. **连续 800~1000ms 低于静音阈值 → 立即发送 `turn_commit`**，不等超时。
3. 建议参数（可按实测调）：
   - 静音判定阈值：振幅 max-abs < 200（约满量程 0.6%），或 RMS < 100
   - 连续静音时长：800ms 起步；环境噪音大可加一倍
   - 防误切：说话总时长 < 300ms 不触发（咳嗽/碰撞过滤）
4. `turn_commit` 发出后立即停止采集，转等 `state` 事件（thinking → speaking）。

**验收**：
- 说「你再讲一个。」（约 1s），`turn_commit` 应在说完后 1~1.5s 内到达（服务端日志 capture_ms ≈ 2000~2500ms）。
- 连续多轮问答，每轮 capture_ms 稳定 < 3s。

## 需求 2（P0）：实现拍照上传（历史问题；现目标为每轮 3 张）

**现状**：服务端从未收到 IMAGE 帧。视觉问答完全不可用（用户问「这是什么」时模型看不到图）。

**要求**：
1. 摄像头（OV2640）初始化失败要有明确串口日志，**失败要重试或上报**，不能静默跳过。
2. 时序：发送 `turn_start` → 收到 `turn_ready` → **采集语音期间抓拍** → 发送图片帧 → `turn_commit`。
3. 图片帧格式（服务端协议）：
   - 一条 WebSocket 二进制消息 = **1 字节前缀 `0x02` + 完整 JPEG**（不允许拆多条）
   - JPEG 必须以 `FF D8` 开头、`FF D9` 结尾（esp_camera_fb_get 返回的即满足）
4. 建议参数：
   - 分辨率 QVGA（320×240）或 VGA（640×480），JPEG 质量中档
   - **单张目标 < 200KB**（降低延迟和内存占用）
   - 当前目标每轮 3 张：开始、中途、提交前；服务端最多接收 5 张，以握手 `max_count` 为准
5. 抓拍时机：VAD 检测到用户开始说话时拍 1 张（或 `turn_ready` 后固定延时 500ms 拍 1 张），**抓拍和音频采集不能互相阻塞**（建议双核分工：核 0 网络+音频，核 1 摄像头）。
6. 收到 `image_received` 事件即确认服务端收到；`INVALID_IMAGE`/`IMAGE_TOO_LARGE` 等错误要打日志。

**验收**：
- 问「这是什么」时，后台本轮 `imageCount=3`、`storedImageCount=3`；摄像头故障时可降级，但不能使用上一轮旧图。
- 后台「ESP32链路日志」详情页能看到图片并能点开放大。

## 需求 3（P1）：处理服务端 `silence_committed` 消息

**背景**：服务端保留静音自动提交兜底。实时链路将兜底延后到至少 3500ms，以免抢在固件提交前末张图片；旧链路仍使用配置阈值。服务端主动提交时会下发：

```json
{"type":"silence_committed","request_id":"...","reason":"silence","silence_ms":3500}
```

**要求**：
1. 收到该消息后：停止采集、丢弃后续音频帧、进入等回答状态（等同自己发了 `turn_commit`）。
2. 统计上报：固件本地计数器记录「服务端兜底触发次数」，串口日志周期性输出（如每 10 轮），用于评估固件 VAD 改进效果。
3. 该消息只是兜底，固件 VAD（需求 1）修好后应极少触发；若频繁触发说明 VAD 参数仍需调整。

---

## 需求 4（P2）：空采集与转写失败

**现状**：偶发「语音转写失败」轮次（2878ms / 504ms），大概率是纯静音/极短噪音采集。

**要求**：
1. `turn_start` 后若 500ms 内能量始终低于阈值（用户没说话），主动发 `turn_cancel` 收尾，不要等到超时。
2. 收到 `turn_ignored`（reason=audio_too_short）事件时给出本地提示音或日志。

## 附：当前协议速查（服务端已就绪）

| 项 | 值 |
|---|---|
| 音频 | PCM16LE 小端、16kHz、单声道、每帧前缀 `0x01`，建议 20~40ms/帧 |
| 图片 | 前缀 `0x02` + 完整 JPEG，单张 ≤2MB，**每轮 ≤5 张**、合计 ≤8MB |
| 握手广播 | `connected.input_image.max_count = 5`（以服务端广播为准，勿写死） |
| 最短有效音频 | 8000 字节（250ms） |
| 单轮最长音频 | 30s（超过会收到 AUDIO_TOO_LARGE） |
| 控制事件 | `turn_ready` / `image_received` / `state` / `turn_ignored` / **`silence_committed`（新增）** |

## 建议实施顺序

1. 需求 1（VAD）——最大收益，多轮每轮省 15~20s
2. 需求 2（拍照）——解锁视觉问答核心能力
3. 需求 3（silence_committed 处理）——配合服务端兜底，半小时的活
4. 需求 4——打磨项

## 2026-09-21 现场复测追加

- 管理后台已确认图片链路可用，但固件每轮仅抓拍 1 张。用户现要求每轮 **3 张**：开始、中途、提交前各 1 张；以设备实际收到的 `connected.input_image.max_count` 为上限。最后一张应尽量贴近 `turn_commit`，避免模型只看到过时画面。3 张是离散快照，不等同实时视频。
- 实测一轮音频采集 20,134 ms、625 KB，模型完成仅 569 ms，TTS 首包 21,074 ms。串口观测环境声 RMS 可达 150–800 以上，固定 RMS 100 / Peak 200 的 VAD 门槛会被环境声持续刷新。结束判定需考虑本轮能量变化，并设置比 20 秒更短的安全上限。
- 验收时核对同一轮后台 `imageCount=3` 且 `storedImageCount=3`、末张图为提交前最新画面；以设备上报的 `speechEndToPlaybackMs` 判断“说完到设备首播”，`commitToFirstAudioMs` 仅代表提交到网关首包。安静环境与电视背景声各测多轮。

## 当前改造验收口径（2026-09-22）

- 唤醒词只负责唤醒，不当作用户问题送模型；唤醒后立即本地预录问题开头，`turn_ready` 到达后冲刷缓存。仅说唤醒词时，设备给出 LED 确认并在等待窗口后取消空轮，不应误标为模型故障。
- 固件以 700ms 连续静音判断说完；末张图片在静音窗口并行预拍，恢复说话则作废重拍。提交前图片最多宽限 280ms，传输失败不得静默丢 PCM 或把旧照片送入下一轮。
- 固件 `turn_commit` 上报 `speech_end_ms`、`speech_end_to_commit_ms`；首次 I2S 写入后上报 `turn_metrics`，包含 `first_audio_received_ms`、`first_i2s_write_ms`。后台以同一设备时钟计算“末次语音→首次 I2S 写入”，旧固件缺字段则显示空值。
- 实时链路 `asrStatus` 是旁路日志转写状态；回答已完成而旁路转写失败时，不应把整轮改为失败。后台应显示本轮 `pipelineMode`、`modelName`，避免新旧链路平均耗时混淆。
- 本次固件与网关改动由用户自行烧录和实测；提交代码不等同于设备端与线上验证通过。
